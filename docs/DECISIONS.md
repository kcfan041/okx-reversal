# 設計決定紀錄

每一項記錄：決定、原因、被放棄的選項。日期皆為 2026-10-08 規劃階段。

| # | 主題 | 決定 | 原因 | 放棄的選項 |
|---|---|---|---|---|
| D1 | 交易所與市場 | OKX，所有 `*-USDT-SWAP` 永續合約 | 依 idea.md 第 14 節 | 現貨、幣本位合約 |
| D2 | K 線週期 | 5m | 假說核心是「巨大 5 分鐘紅 K」 | 1m（資料量 5 倍） |
| D3 | 歷史期間 | 回補 1 年，之後持續累積 | 樣本數夠，下載量可接受 | 6 個月（樣本少）、2 年以上（多數新幣沒資料，下載太久） |
| D4 | 資料來源 | OKX 公開 REST API | 不需帳號，可增量更新 | OKX 歷史資料下載頁（需另外解析每日檔案，第二版再考慮用來補下架幣） |
| D5 | 儲存 | 單一 DuckDB 檔 | 可增量寫入並依主鍵去重；查詢快；檔案小；不需伺服器 | 每檔一個 Parquet（增量要整檔重寫）、SQLite（檔案大 3～4 倍、統計慢） |
| D6 | 資料處理 | pandas | 最通用，好除錯 | Polars（較快但第一版不需要） |
| D7 | 執行機 | Windows 主機 24/7 | 使用者主機幾乎全天開機；開發機不常駐 | 開發機手動下載、GitHub Actions（美國 IP 會被 OKX 擋）、VPS（第二版再考慮） |
| D8 | 排程 | Windows 工作排程器，每 5 分鐘，單次最多 4 分鐘 | 內建、不需常駐程式；`IgnoreNew` 天然防重複；關機後錯過的會補跑 | 常駐 daemon（要處理崩潰重啟）、Windows Service（設定複雜） |
| D9 | 資源 | 低優先權、`pythonw`；限速依端點分開：history-candles 每秒 8 次（實測上限約 10）、candles 每秒 15 次、其他每秒 5 次；連續被限速自動降速（2026-10-08 修訂，原為全域每秒 5 次） | 使用者要求不能耗太多效能，但同意加速首次回補；CPU 幾乎不變，回補期間流量約每秒 1 MB 內，回補完成後每輪只剩 forward 約 40 秒 | 全域每秒 5 次（首次回補約 2.7 天）、每秒 9～10 次（429 較多） |
| D10 | 回補順序 | 分層：30 → 90 → 180 → 365 天 | 資料還沒補完時，回測也能涵蓋全部合約 | 一檔補完再換下一檔（部分資料時只有少數幣可用） |
| D11 | 下架合約 | 標記 delisted 並保留資料 | 系統運作後才下架的幣不再有倖存者偏差 | 刪除 |
| D12 | 過去已下架的幣 | 第一版不補，報告註明偏差 | REST 查不到（實測回 51001）；補救成本高，先看結果是否值得 | 立即研究歷史資料頁 |
| D13 | 成交量欄位 | `volCcyQuote`（USDT 成交額） | 跨幣種可比較 | `vol`（張數，每檔面值不同） |
| D14 | 進場價 | 紅 K 後下一根開盤價 | 事件在紅 K 收盤才確認，較貼近實際能成交的價格 | 紅 K 收盤價（會高估） |
| D15 | 預設門檻 | 24h 漲幅 > 50% 或 6h > 30%；紅 K <= -8%；量能 >= 20 根均量 × 4；冷卻 24h | idea.md 第 4 節；6h 條件捕捉更快的暴漲 | — |
| D16 | 參數掃描 | 紅 K -5/-8/-10/-15% × 量能 3/4/6 倍 | idea.md 第 4.2 節；看結果對門檻的敏感度 | 更大的格點（多重比較問題更嚴重） |
| D17 | 對照組 | `random_any` 與 `random_pump` 兩組隨機基準 | 沒有對照就無法判斷是否為 edge；`random_pump` 區分「紅 K 本身的資訊」與「暴漲後本來就會跌」 | 只看事件本身 |
| D18 | MAE/MFE 定義 | 以做空角度，24h 視窗，另記錄先後順序 | idea.md 第 9 節強調中間路徑 | — |
| D19 | BTC 環境 | 以 BTC 4h 報酬 ±1% 分 strong/neutral/weak，另記錄是否低於 24h EMA | 簡單、可解釋 | 波動率分組（第二版） |
| D20 | 成本 | 每邊手續費 0.05% + 滑價 0.05%；不含 Funding | 保守估計；Funding 第二版加入 | 不計成本 |
| D21 | 圖表 | 純 matplotlib 自繪 K 線 | 少一個依賴 | mplfinance、Plotly |
| D22 | 第一版不做 | OI、Funding、清算、Order Book、lower high、Scanner、自動交易 | 先驗證最原始假說（idea.md 第 14 節） | — |
| D23 | Git | 只放程式、設定、文件、`events.csv`、`summary.json`、`sweep.csv` | 資料約 1 GB 且持續變動，可由程式重建 | Git LFS（免費額度 1 GB 會用完）、zip 放 Releases |
| D24 | Repo | `kcfan041/okx-reversal`，私人 | 使用者要求名稱短、私人 | — |
| D25 | 開發方式 | 規劃機只寫文件並上傳；實作在另一端進行 | 使用者要求 | 在規劃機寫程式但不測試 |
| D26 | 時間 | 全部 UTC，資料庫存毫秒整數 | 與 OKX API 一致，避免時區錯誤 | 本地時間 |
| D27 | 套件管理 | uv：`pyproject.toml` + `uv.lock`，Python 3.12 由 uv 安裝；排程仍直接呼叫 `.venv\Scripts\pythonw.exe` | 主機已有 uv 與 3.12；lock 檔保證重建一致；`uv sync` 一步完成部署 | `requirements.txt` + pip（無 lock）、只用 uv 建 venv |
| D28 | 網頁監控台 | FastAPI + uvicorn，單頁 HTML/JS，lightweight-charts（vendor 進 repo），只綁 127.0.0.1，手動啟動 | 不需 node 建置；互動 K 線；本機即可，不必處理登入 | Streamlit（控制與自動刷新不順）、純標準庫（繁瑣）、常駐服務 |

| D30 | 網頁讀資料庫 | 每個請求唯讀開啟、查完立即關閉 | DuckDB 讀寫互斥，不可長時間占用而擋住 sync | 常駐連線 |
